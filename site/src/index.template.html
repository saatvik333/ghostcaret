How it works

This is how it works on my niri setup today. It hasn't been tested on other machines yet.

After a short pause in your typing, a suggestion appears after the cursor, in the field's own font where the platform allows it. If the letters you type next match it, it gets shorter instead of starting over. Anything else removes it: a different letter, moving the cursor, clicking, switching apps or Esc.

Keys

Tab
Takes the next word. It is only captured while a suggestion is showing, so the app gets Tab as usual the rest of the time.
`
Takes the whole suggestion. To type a literal backtick while a suggestion is showing, press Esc first.
Alt+→
Shows more. It is Option+→ on macOS.
Esc
Dismisses the suggestion.

All of them can be changed in settings.

How much it suggests

You set the most a suggestion may show. The demo above has the same control.

Word
Stops at the end of the next word.
Phrase
Stops at a natural pause such as a comma or a conjunction, usually 3 to 6 words.
Sentence
Stops at the end of the sentence.
Paragraph
Stops at the end of the paragraph, or at a word cap you set.
Auto
Stops where the model's confidence drops below your boldness setting. This is the default.

Boldness is a slider from careful to bold. Auto also has a ceiling that depends on the kind of app: up to a sentence in chat, up to a paragraph in email, documents and notes, and one word in search boxes. Each app can have its own length and ceiling, or be switched off.

Where it stays quiet

  • Password and other secure fields.
  • Address bars.
  • Code editors, unless you turn it on for that app.
  • A terminal at a plain shell prompt, so Tab keeps completing commands. It should work for prose inside terminal apps.
  • An empty field, until you have typed something.
  • Anywhere the model is less sure than your boldness setting asks for.

{{replyName}}

Tap the right Alt key on its own. In a chat or email reply box, {{name}} reads the visible conversation and offers three short directions, like “accept and suggest Tuesday”, plus a field for your own. Picking one writes a draft into a preview card, and you accept it into the text box, edit the direction or close the card. With text selected, the same key opens a card with Fix, Rephrase, Shorten, Expand, Translate and Change tone, plus actions you define. Accepting replaces the selection, and one undo brings the original back.

It shows exactly what will be inserted, and it never sends anything or presses Return. If it can't read the conversation it says so, and you can type a direction yourself. Reading a screenshot is off by default.

Models and privacy

Same caveat as above: this is the design, and none of it is built end to end yet.

A local model

Inference runs on your machine through llama.cpp, and any GGUF file works. Setup checks your memory first. With 16 GB or more it offers the standard model, about 3 GB. With less it offers a smaller one, or suggests using a key. Downloads resume after an interruption and are checked against a published hash before use.

Your own API key

Pick a provider: any OpenAI-compatible endpoint (OpenAI, OpenRouter, Groq, Together, Ollama, LM Studio, llama-server, vLLM and similar), Anthropic, or Gemini. Paste the key and test it with one request. Keys go in the system keychain. Cloud use shows a request counter, with an optional daily cap.

Autocomplete and replies each have their own model setting, so a local model for one and a key for the other is fine.

What leaves your machine

  • With a local model, the design keeps your text on the device.
  • With your own key, only the context for that one request leaves, after a filter removes API keys, access tokens, card numbers and password= style pairs. A “What was sent” view lists every cloud request from the session: the provider, the model and the exact text. It lives in memory and is cleared when you quit.
  • It is built to send no telemetry. The network is for model downloads you start, the update check (which you can turn off) and the provider you set up.
  • Password and other secure fields are not read. Password managers are on the blocked-apps list by default, and you can add any app.
  • Screenshot reading, the clipboard and style learned from your sent messages are off by default.
  • Text read from the screen, the clipboard or a conversation is treated as data, so instructions inside it can't change what {{name}} does.

The network test that would check the privacy points is planned, not written. {{#if repoUrl}}The source is on GitHub if you want to follow along.{{else}}The source isn't public yet.{{/if}}

Platforms and status

Nothing is released yet. Linux (Wayland) comes first and runs end to end on niri. Windows is built and waiting for its first test on a real Windows machine, and macOS comes later.

Linux (Wayland)

In development

{{name}} is the input method itself, so the suggestion appears in a small panel at the cursor. That needs a compositor that supports the Wayland input-method protocol. niri 26.04 does, and it's what I test on. Other compositors with that protocol should work too, but only niri is tested so far. KDE Plasma, GNOME and X11 come later.

Only one input method can be active, so it can't run next to fcitx5 or IBus. Firefox works as it is; Chrome needs --enable-wayland-ime --wayland-text-input-version=3.

Windows

In development

Faint text drawn at the cursor. It can't reach apps running as administrator unless {{name}} runs elevated as well.

macOS

Later

Faint text drawn at the cursor. It needs the Accessibility permission and pauses while another app holds Secure Input. Where a browser hides the cursor position, a card above the field is used instead.

What a release has to meet

Targets, and where it stands

These are the numbers a release has to meet. The first measurements, on my laptop and not on a reference machine, miss some of them: a suggestion takes about 240 ms at the median with a small local model on the CPU. A release that misses one doesn't ship. The current numbers are in the quality doc.

  • 100 msFrom your last keystroke to a visible suggestion, at the median, with a local model. 250 ms at the 95th percentile.
  • 50 µsTime in the key handler, at the 99th percentile. Typing never waits for a suggestion.
  • 0 CPUWhile you are not typing. No polling timers, only operating-system events.
  • 100 MBMemory across all processes with no model loaded.
  • 40 MBInstaller size, models excluded.

I want each release to come with its benchmark report: keystrokes saved and the share of wrong suggestions. Any comparison with another tool will link to the test it came from.

Questions

Can I download it?

Not yet. It runs on my machine; the first test builds go to early testers.

What will it cost?

It is meant to be free, with no paid tier and no account. If you use your own API key, your provider bills you at its own rates.

Is it open source?

{{#if licensePublished}}Yes, under {{license}}.{{else}}It will be, under {{license}}.{{/if}} {{#if repoUrl}}The source is on GitHub.{{else}}The source isn't public yet.{{/if}}

{{#if aiDisclosure}}
Who is writing it?

{{aiDisclosure}} The design is mine, and the code is written from public operating-system documentation and APIs.

{{/if}}
Will it work in my app?

The goal is the places people write: browser text boxes, chat, notes and documents, terminals and email. I don't know yet which apps will work. The plan is a checklist of about 20 apps per platform. Where placing the suggestion fails in an app, it falls back to a card, and the release notes list the failure.

Does what I type go to a server?

With a local model, the design keeps it on your device. With your own key, the context for each request goes to that provider after the secret filter has run, and the “What was sent” view shows exactly what.

Can it run next to fcitx5 or IBus?

No. On Linux it is designed as an input method itself, and only one input method can be active at a time.
